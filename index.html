Hardware-aware optimization of deep learning models for real-time edge AI

We take two models that must run together on a small ARM board, a YOLOv8n person detector and a gas-hazard classifier, shrink them from 32-bit floats to 8-bit integers, and measure what that actually changes on the device: latency, frame rate, memory, CPU load, heat and accuracy.

The problem

Edge devices have a fixed amount of compute, memory and thermal headroom. A model that is accurate on a workstation can be too slow, too large or too hot once it shares a 4-core ARM CPU with a second model.

Optimization is often reported as a single number from a desktop. We instead deploy on the target hardware and compare every model form under the same conditions.

What we measure

Latency (median and 95th percentile), frames per second, model size, RAM, CPU utilization, temperature and throttling, and the accuracy retained after quantization.

Each model is measured alone and with both models running at the same time, because that is how the system is actually used.

System

Training and conversion run offline. Inference, fusion and benchmarking run on the edge board. A microcontroller handles sensors and actuation.

Offline (Colab)

Train and optimize

Gas MLP trained on the UCI Gas Sensor Array Drift dataset. Both models converted to TFLite FP32 and full-integer INT8 with a representative calibration set.

Raspberry Pi 4B

Infer, fuse, measure

Camera thread keeps only the newest frame. YOLOv8n INT8 detects people, the gas MLP classifies hazard level, and a fusion rule sets the safety state.

Arduino Uno

Sense and act

Reads MQ-2 and DHT-11, streams readings over serial, and drives LEDs, buzzer and relay from the SAFE, WARNING or ALARM command.

Optimization pipeline

Both models go through the same three stages, and each stage is evaluated before moving on.

Stage 1

FP32 baseline

  • YOLOv8n PyTorch, 320×320 input
  • Gas MLP 128 → 64 → 32 → 3 in Keras
  • Reference for accuracy and detections
Stage 2

TFLite FP32

  • Same precision, edge runtime
  • Isolates the effect of the runtime from the effect of quantization
Stage 3

TFLite INT8

  • Post-training full-integer quantization
  • Calibrated on training-split samples
  • Re-evaluated on held-out data

Results: person detection on video

The same video frames are passed through every model form. Each model runs its own pass with warm-up excluded, so the timings do not interfere.

Results: gas-hazard classifier

The UCI dataset labels six gases. We derive SAFE, WARNING and CRITICAL from per-gas concentration tertiles fitted on the training split only, and report both a random split and a drift-aware split that tests on later sensor batches.

How to read these results

Latency is model-only time. Image resizing, post-processing, camera capture and serial transfer are logged separately and never added to the model figure.

The device matters. INT8 gives a large speed-up on ARM cores. On x86 cloud CPUs the gain can be small, so every result on this page names the processor it was measured on.

Detection quality is reported as agreement with the FP32 model on the same frames, because no labelled evaluation set is used for the person class.

The gas model's demo input is replayed held-out UCI vectors, because a single MQ-2 cannot produce the dataset's 128 features. Live MQ-2 and DHT-11 readings are logged as the start of a calibration dataset.
